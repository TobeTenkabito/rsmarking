# 沙箱失败定位与回归（2026-11-13）

## 原始故障

检查最近一次“你能用工作空间的文件帮我提取海岸线吗？”的持久会话及工具记录，使用其中保存的完整脚本和同一组四波段影像重放。没有重新生成脚本，也没有修改原始影像。

1. 第一版脚本从矩形影像的最外侧行列寻找海水，但旋转影像外围存在无效值，因而没有找到候选连通域。规划提示现在要求检查有效数据覆盖边界，并区分海洋、内陆水体和裁剪边界。
2. 后续脚本改用有效数据边界，已经写出 GeoJSON，却在打印 `source_vertices` 统计值时失败：`TypeError: Object of type int64 is not JSON serializable`。执行器因此按失败处理，未交付临时输出。
3. 工具错误只保留开头，长元数据和堆栈挤掉了真正的异常原因；后续排查和验收还触发了原有调用预算上限。
4. 修复序列化后，同一脚本产生的全景矢量文件为 10,114,928 字节，进一步暴露出接收、保存、检查与工作区导入链路的 5 MiB 限制。现在这几个环节统一采用已有产物大小上限 20 MiB，保留要素数量与几何检查。

## 修改

- 仅向用户脚本提供兼容 NumPy 的 `json.dump` / `json.dumps`，支持整数、浮点数、布尔值及数组，保持数值类型。标准库和第三方库使用的 JSON 模块不变。
- 提供 `write_geojson(document)`，校验基本结构、文件后缀、目录边界、非有限数值和文件大小；后续网关继续负责几何校验及保存。
- 输出文件按请求格式查找。未使用指定文件名时，只接受唯一的同格式候选；拒绝目录和符号链接。异常退出仍然是失败，不把残留文件直接当作合格成果。
- 错误先完整脱敏，再保留开头与末尾，让模型能看到实际异常。
- 按本次要求，默认不设累计 Token、模型调用、工具调用或工具交互轮数上限；调用方显式传入的限额继续生效。单次上下文容量、沙箱超时、权限边界和有限自动返工仍然生效。
- 规划复用已知输入，验收优先检查实际成果；没有成果时根据执行错误反馈返工，避免重复发现工作区。
- 调整镜像构建层顺序，使运行脚本变化不再使系统和 Python 依赖安装层失效。

## 自动回归

- AI、执行器和沙箱相关后端测试：284 项通过，包含大于旧 5 MiB 上限的完整交付链路及超过 20 MiB 的拒绝路径。
- 前端单元测试：119 项通过。
- 浏览器测试：10 项通过。
- 用模型替身完成 37 次模型调用、34 次工具调用的协作任务，跨过旧上限；另验证累计估算用量超过旧 Token 上限仍可记录。

这些自动回归不等于新一轮真实模型独立验收。实际影像重放与工作区写入检查另行记录，科学精度也不能仅由脚本成功或几何有效性证明。

## 实际影像重放

原脚本在修复后的 Docker 沙箱中成功运行，未改脚本算法；使用现有 4 GB 内存、2 核 CPU 和 300 秒执行超时。输出包含 6,174 条 LineString，0 空几何、0 无效几何，WGS84 范围为 `[120.89167880121181, 30.701493213129606, 122.94830020029566, 32.76956290027395]`。

结果保存在忽略提交的 `storage/raw/coastline_bug_replay_20261113_after.geojson`。本次重放没有调用模型 API，未重新完成真实模型的规划、验收与返工全流程；这些流程的故障路径由自动回归覆盖。输出只是原算法的重放结果，不能将几何有效性视为海岸线科学精度验收。

同一文件经产物保存和独立检查后，在真实 PostGIS 的临时 schema 中导入 6,174 条要素。验证两次并发导入复用同一图层、要素不重复，导出后的属性一致，坐标误差在 GeoJSON 导出的小数精度范围内（`1e-9` 度）。另以小型 GeoTIFF 验证入库去重、COG 和像元保持。测试 schema 和临时产物已清理，原项目记录没有变化。
